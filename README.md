# ShareTrip Contract Service

## Назначение сервиса

Contract Service — отдельный микросервис ShareTrip, отвечающий за управление договорными отношениями между системой и компаниями-клиентами.

Основная бизнес-ответственность сервиса — определять, может ли конкретная компания использовать определённую услугу ShareTrip согласно условиям своего договора.

Сервис выделен отдельно не из-за наличия сущности `Contract`, а потому, что у него есть самостоятельная бизнес-ответственность: управление договорными условиями клиента и проверка доступности услуг.

## Ответственность сервиса

Contract Service отвечает за:

- хранение информации о договорах;
- контроль статуса договора;
- хранение периода действия договора;
- хранение условий договора;
- хранение списка доступных компании услуг;
- проверку доступности конкретной услуги;
- предоставление API другим сервисам;
- владение собственной схемой данных.

Договор может находиться в одном из состояний:

- `draft` — договор создан, но ещё не действует;
- `active` — договор активен;
- `suspended` — договор временно приостановлен;
- `terminated` — договор расторгнут.

Договор также содержит дату начала и дату окончания действия.

Доступные услуги:

- `trip_creation` — создание поездок;
- `trip_participants` — добавление участников поездки;
- `notifications` — отправка уведомлений;
- `premium_support` — расширенная поддержка.

## Что входит в границу сервиса

В границу Contract Service входят:

1. Создание договора для компании.
2. Получение договора по идентификатору.
3. Получение активного договора компании.
4. Изменение статуса договора.
5. Добавление или обновление списка доступных услуг.
6. Проверка доступности конкретной услуги для компании.

API сервиса описан в `api/contract.yaml`.

## Что не входит в границу сервиса

Contract Service не:

- создаёт и не изменяет поездки;
- управляет жизненным циклом поездки;
- отправляет уведомления;
- хранит пользователей;
- определяет, кто залогинен в системе;
- проверяет роли пользователя;
- управляет каналами доставки уведомлений;
- отвечает за оплату и счета;
- хранит юридические файлы договоров;
- хранит историю изменений договора.

Пользователи и роли находятся в зоне ответственности Keycloak и слоя авторизации вызывающего сервиса. Поездки остаются в ShareTrip, а уведомления — в Notification Service.

## Взаимодействие с другими сервисами

Основным потребителем Contract Service является ShareTrip.

Сценарий создания поездки:

1. Пользователь отправляет запрос на создание поездки в ShareTrip.
2. ShareTrip получает идентификатор компании пользователя.
3. ShareTrip обращается в Contract Service.
4. Contract Service проверяет договор компании.
5. Contract Service возвращает результат проверки.
6. Если услуга доступна, ShareTrip создаёт поездку.
7. Если услуга недоступна, ShareTrip возвращает ошибку пользователю.

При этом ShareTrip не должен обращаться напрямую к базе данных Contract Service. Взаимодействие выполняется только через внешний API сервиса.

## Основные бизнес-правила

У компании может быть только один активный договор.

При проверке доступности услуги Contract Service должен учитывать:

1. существует ли у компании активный договор;
2. не истёк ли срок действия договора;
3. не начинается ли договор только в будущем;
4. включена ли требуемая услуга;
5. не находится ли договор в статусе `suspended` или `terminated`.

Если все условия выполнены, сервис возвращает положительный результат.

Если хотя бы одно условие не выполнено, сервис возвращает отрицательный результат и причину отказа.

Таким образом, основной бизнес-вопрос Contract Service:

> Может ли компания использовать конкретную услугу?

## Внешний API

Внешний API описан в файле [`api/contract.yaml`](api/contract.yaml) в формате OpenAPI.

API предоставляет операции для:

- создания договора;
- получения договора;
- получения активного договора компании;
- изменения статуса;
- обновления доступных услуг;
- проверки доступности услуги.

API выражает бизнес-операции сервиса и не раскрывает внутреннюю структуру базы данных.

## Хранение данных

Contract Service владеет собственной схемой данных.

Минимально сервис хранит две области данных:

- договоры;
- услуги, доступные по договору.

Схема должна позволять хранить идентификатор договора, идентификатор компании, статус договора, даты начала и окончания действия, список услуг и признак доступности каждой услуги.

SQL-миграции находятся в каталоге `migrations/`.

## Проверка границы сервиса

Граница сервиса считается корректной, если:

- ShareTrip может работать с договорами через API без прямого доступа к базе Contract Service;
- внутренняя схема хранения может изменяться без изменения контракта API;
- в Contract Service отсутствует логика создания или управления поездками;
- в Contract Service отсутствует логика отправки уведомлений;
- в Contract Service отсутствует логика аутентификации и проверки ролей;
- из API понятно, какие бизнес-решения принимает сервис.

Contract Service не должен превращаться в простой CRUD над таблицей `contracts`. Его основная ценность — бизнес-проверка договорных условий и доступности услуг.

## Статус проекта

На текущем этапе реализации бизнес-логики на Go не требуется. Основная задача — определить границу Contract Service, его внешний API-контракт, схему хранения данных, миграции и бизнес-правила проверки доступности услуги.
